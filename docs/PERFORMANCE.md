# Performance

This document records Reframe's performance targets, how to measure them, and
the results that have actually been collected. Anything not measured is
labelled **goal**. Lab numbers (Lighthouse, scripted Chrome) are not field
data and don't prove real-user performance.

## Targets

| Metric | Target | Status |
|---|---|---|
| Lighthouse mobile performance | ≥ 90 | **Met in lab**: 100 (local production build) |
| Largest Contentful Paint | ≤ 2.5 s | **Met in lab**: 1.12 s (simulated mobile) |
| Interaction to Next Paint | ≤ 200 ms | **Goal**: no field data yet. Lab proxy: slowest input event during a 30-step slider drag was 32–40 ms |
| Cumulative Layout Shift | ≤ 0.1 | **Met in lab**: 0 (was 0.096) |
| Long tasks (> 50 ms) during normal editing | Minimise | **Met in lab**: 0 during 5 s playback and a 30-step slider drag |
| UI responsiveness during export | No prolonged blocking | **Met in lab**: 0 long tasks, worst frame gap 17–33 ms across all exports |
| Export regression tests | All pass | **Met**: `bun run test`, 175 tests |
| Resource cleanup | No accumulation over export/cancel cycles | **Met in lab**: worker count stable over 3 export→cancel cycles |

Field targets (INP, LCP and CLS at p75) need Datadog RUM data with enough
traffic. They are goals until that data exists.

## Test environment (for every number below)

- Apple M3 Pro (11 cores, 18 GB RAM), macOS 26.3.1
- Chrome 155.0.8059.85 (headless), Lighthouse 13.5.0
- Lighthouse runs use the default mobile preset: simulated throttling, 4× CPU
  slowdown, 150 ms RTT, ~1.6 Mbps.
- **Local production build** (`bun run build`, the static `out/` directory),
  served by `scripts/perf/serve.mjs` with brotli. Unless stated otherwise it
  sends the same COOP/COEP and security headers as `vercel.json`.
- Interaction benchmarks use a 1440×1000 viewport and a synthetic fixture: 6.02 s,
  640×360, H.264 + AAC, 571 KB, generated by `scripts/perf/make-fixture.js`.
- "Before" is `main` at `4af01e5`; "after" is this branch.

## Results

### First page load (Lighthouse mobile, median of 5)

| | Perf | FCP | LCP | TBT | CLS | A11y | Transfer |
|---|---|---|---|---|---|---|---|
| Before (local build) | 86 | 2.38 s | 3.40 s | 47 ms | 0.096 | 95 | 315 KB |
| **After (local build)** | **100** | **0.90 s** | **1.12 s** | **19 ms** | **0** | **100** | **258 KB** |
| Live deployment, before (3 runs, 2026-10-21) | 91 | 1.79 s | 2.80 s | 36 ms | 0.096 | 92 | 280 KB |

Where the gain came from (Lighthouse diagnostics, before → after):

- **Render-blocking Google Fonts `@import` removed.** It loaded Inter, Roboto,
  Poppins and Montserrat. No CSS used them, and Lighthouse attributed about
  930 ms of blocking to it. The UI now uses the platform font stack, with no
  font requests at all.
- **CLS 0.096 → 0.** The privacy notice mounted hidden and then appeared after
  hydration, pushing the upload area down. It now renders in the static HTML;
  for visitors who dismissed it, an inline script hides it before first paint.
- **Less JavaScript before first paint.** The Datadog SDK (~53 KB) now loads
  as a separate chunk at idle, and the looping Lottie upload animation
  (`lottie-web`, ~63 KB) is replaced by a static icon. Lottie now loads only
  for the one-shot success animation.

## Problems found and fixed

1. **Global transitions.** `*, *::before, *::after` transitioned colour
   properties on every node, and `button { transition: all }` applied
   everywhere. Both are gone. Controls use explicit 120–220 ms transitions,
   and theme changes crossfade only for 200 ms around an explicit toggle.
2. **Playback re-rendered the whole editor.** `useVideoEditor` mirrored
   `timeupdate` into React state through an effect with no dependency array,
   which re-subscribed on every render. The playhead is now read on demand,
   and only the frame strip subscribes; it updates state only when the
   active frame changes.
3. **The URL updated on every slider tick.** `history.replaceState` ran on
   every recipe change; it is now debounced to 250 ms. Safari throws after
   100 calls in 30 s. The sync also wrote `textOverlays` (an array) into the
   query string as `"[object Object]"`, which broke reloads.
4. **Thumbnail extraction.**
   - Frame count is now capped at 48 for long videos.
   - Every seek has a timeout; before, a seek that never fired `seeked`
     hung forever.
   - Work is abortable, and every object URL is either handed off or revoked.
   - The decoder is released when extraction finishes.
   - React updates arrive in batches of 6 frames.
   - The first frame no longer renders black: extraction waits for
     `loadeddata`, not `loadedmetadata`.
   - Failures show a recoverable message with a retry.
5. **Progress was flooded.** FFmpeg reports progress per frame; both the
   worker and the client now forward only whole-percent changes. The dialog
   also opened at "100%", left over from engine load; it now starts at 0%.
6. **Duplicate metadata load per export.** The export now reuses the
   duration the editor already has.
7. **A failed export could poison the next one.** After a non-cancel failure
   the worker is restarted, so Retry starts from a clean engine and
   filesystem. Settings are always kept.
8. **Terminating during engine load left the load promise pending forever.**
   It now rejects.
9. **The `-t` output-duration fix (#1289) never reached the worker.** It only
   changed the unused main-thread copy of `buildArguments`. The worker now
   always passes `-t`, which prevents endless exports with looped music on
   silent clips.
10. **The multi-threaded core deadlocked.** On "auto" thread count,
    libx264/libvpx asked for more threads than the core-mt pthread pool holds.
    Encoder threads are now capped at 4 when cross-origin isolated (see
    "Cross-origin isolation" below).
11. **`ResizeObserver` for preview sizing.** It replaces a `window` resize
    listener that missed layout-driven size changes. Sub-pixel changes no
    longer re-render.
12. **A drop on the drop zone was handled twice**, once by the zone and once
    by the document listener, so validation and metadata extraction ran twice.

## Cross-origin isolation: production finding (needs a maintainer)

The live deployment sends **none** of the headers in `vercel.json`. On
2026-10-21, `curl -sI https://reframe-lilac.vercel.app/` showed only Vercel's
default `strict-transport-security`: no COOP/COEP, `X-Frame-Options`,
`X-Content-Type-Options`, `Referrer-Policy` or `Permissions-Policy`.

The likely cause is that `vercel.json` combines the legacy `routes` key with
`headers`, which Vercel documents as mutually exclusive. This has not been
verified on Vercel. Consequences:

- Production runs the **single-threaded** core (exports are 4–4.5× slower
  than multi-threaded in the table above).
- The intended security headers are not applied.
- Until this branch, **turning the headers on would have broken exports**:
  the multi-threaded path deadlocked (fix 10).

`vercel.json` is deliberately unchanged here. Suggested follow-up: remove the
`routes` block (`handle: filesystem` is already the default for static
output), deploy a preview, confirm the headers with `curl -sI`, and run an
export on the preview before promoting it.

## Datadog RUM

Configured in `src/components/DatadogInit.tsx`, with helpers in
`src/lib/telemetry.ts`.

- The SDK loads lazily at idle. Calls made before it is ready are queued
  (up to 50) and replayed. Every call is wrapped, so a telemetry failure can
  never interrupt editing.
- Session replay stays disabled (`sessionReplaySampleRate: 0`).
- Privacy:
  - `enablePrivacyForActionName: true`, because auto-named clicks could
    otherwise carry the file name.
  - `beforeSend` strips query strings, where recipe settings live, from view
    URLs and referrers, and drops `blob:` resources.
  - Custom events carry only buckets and enums, never file names, captions,
    paths or exact values.
- `NEXT_PUBLIC_DATADOG_ENV` (default `production`) lets local and preview
  runs be separated.

| Event | Type | Properties |
|---|---|---|
| `ffmpeg_init` | duration vital + action | `threading` (`multi`/`single`), `durationMs` |
| `ffmpeg_load_success` / `ffmpeg_load_failure` | action | `durationMs`, `threading` / `reason` |
| `export_start` | action | `format`, `resolution` bucket, `input_size` bucket, `clip_length` bucket, `has_text`, `has_music`, `has_image_overlay` |
| `export` | duration vital + action | encoding time only (engine start is `ffmpeg_init`) + the above |
| `export_success` | action | the above + `output_size` bucket, `durationMs` |
| `export_failure` | action | the above + `stage` (`engine`/`encode`), `category` (`engine`/`network`/`codec`/`memory`/`ffmpeg`) |
| `export_cancel` | action | `stage`, `durationMs` |
| `thumbnails_generated` | duration vital + action | `frames`, `skipped`, `durationMs` |
| `thumbnails_failed` | action | `reason` (`timeout`/`decode`) |
| Global context | — | `cross_origin_isolated`, `shared_array_buffer`, `cpu_cores` bucket, `device_memory_gb` bucket, `reduced_motion` |

Slow interactions and long tasks come from RUM's built-in collection
(`trackLongTasks: true`, plus INP/LCP/CLS on view events), so no custom code
duplicates them.

Suggested dashboard widgets (not created here; there is no Datadog account
access from this change):
- p75 `@view.interaction_to_next_paint`, `@view.largest_contentful_paint`
  and `@view.cumulative_layout_shift`, by `@device.type`.
- p50/p90 of the `export` vital by `@context.resolution` and
  `@context.cross_origin_isolated`.
- Count of `export_failure` by `@context.category` and `@context.stage`.
- p90 of the `ffmpeg_init` vital by `@context.threading`.

## How to measure

```bash
# Unit/regression tests (CI-safe; no real video or network)
bun run test

# Production build served like production
bun run build
node scripts/perf/serve.mjs out 4300              # with COOP/COEP (vercel.json intent)
NOISO=1 node scripts/perf/serve.mjs out 4301      # without (what production serves today)

# Lighthouse, mobile preset, 5 runs, prints per-run and median
scripts/perf/lighthouse.sh http://localhost:4300/ local 5
scripts/perf/lighthouse.sh https://reframe-lilac.vercel.app/ live 3

# Browser scenarios need puppeteer-core (not a project dependency)
npm i --no-save puppeteer-core     # or: PUPPETEER_CORE=/path/to/puppeteer-core
node scripts/perf/make-fixture.js 6 640 360 scripts/perf/fixtures/sample-6s.mp4 http://localhost:4300/privacy
node scripts/perf/bench.js http://localhost:4300/ after scripts/perf/fixtures/sample-6s.mp4
node scripts/perf/motion.js after=http://localhost:4300/
```

`bench.js` covers:
- upload and metadata
- 5 s of playback
- rapid slider adjustment
- thumbnail generation
- a failed engine load (CDN blocked) followed by retry
- exports at 720p, 1080p and 1080×1920
- three export→cancel cycles with worker counts
- an export after cancelling

It writes `bench-<label>.json`. Exports fetch the FFmpeg core from jsDelivr,
so they need network access. These scenarios are not part of CI.

Local builds with Datadog keys in `.env.local` send real RUM events. Set
`NEXT_PUBLIC_DATADOG_ENV=local-perf` (or leave the keys unset) when
benchmarking.

## Known bottlenecks and limitations

- **Memory.**
  - Export reads the whole input into an `ArrayBuffer`. It is *transferred*,
    not copied, main → worker → FFmpeg's worker; the results come back the
    same way. Then MEMFS copies it into the WASM heap, so peak memory is
    about 2× the input, plus the output.
  - Mounting the `File` with WORKERFS would avoid both copies. It is the
    highest-value next step for large files, but it changes how inputs are
    addressed and needs browser validation.
- **Large-file benchmarks were not run.** The ~100 MB and ~500 MB scenarios
  need representative real footage; `make-fixture.js` records in real time
  and isn't suited to that. These remain goals.
- **Duplicated FFmpeg logic.** `ffmpeg.ts` and `ffmpeg.worker.ts` each have
  their own `buildVideoFilter`/`buildArguments`. Only the worker's copy runs,
  but unit tests exercise the main-thread copy. Consolidating them would stop
  fixes landing in the wrong copy, as happened with #1289.
- **Cancellation terminates the worker.** It is reliable, but the next
  export recompiles the engine (~2.5 s from HTTP cache).
- **Blob URLs from engine load are held for the worker's lifetime** (~32 MB);
  terminating the worker releases them.
- **No field data yet.** The INP target in particular is unverified until
  RUM shows p75 values.
